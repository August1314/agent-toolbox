# reuse-first：先复用后自建

> 通用方法论 skill，让任意 Agent（Claude Code / Codex / WorkBuddy / Gemini / opencode…）
> 在动手产出之前先找现成成果，直接搬过来用，而不是自己烧 token 重造一遍。

- 日期：2026-11-02
- 状态：设计已确认，待实现
- 形态：独立 git 仓库 `~/agent-toolbox/`，一份资产 + 一份 SKILL.md，全 agent 挂接

---

## 1. 问题陈述

很多任务里，最贵的不是"想清楚怎么做"，而是**某几个具体环节的实现细节**：
解析带合并单元格的 PDF 表格、把音轨对齐到视频帧、给 WebGL 场景做后期、
把一个数据集切成正确的 train/val 划分。

这些环节别人已经做过，而且往往**已经烧掉了大量 token** 才把边界情况踩完。
我们现在自己再实现一遍，等于把别人付过的学费再付一次。

### 1.1 核心原则

> **搬进来的是工具本身，不是重新推导的结论。**

这条原则区分了两种看起来相似、代价差一个数量级的做法：

| | 做法 | token 代价 |
|---|---|---|
| ✗ 复现 | 拿到源码后读懂、改写、按自己的理解重写一遍 | 与从零实现几乎相同，外加额外的理解成本 |
| ✓ 复用 | 把别人的工作装进工具箱，写薄 adapter 调用它 | 接近零，仅剩装配成本 |

**这不是"复现"。** 复现是我们要消灭的行为。

### 1.2 与原始灵感的对应

灵感来自一个抖音视频，讲 AI 动效工具 Motion Face 的做法：

1. 不是靠模型能力强，而是靠**先把数据流跑通并蒸馏固化**
2. 借鉴 Remik 方案：复现已有成果 → 预跑 → 用已有产物做增量 → 把训好的东西打包成可重复调用的交付物
3. 结论原话：*核心不是模型能力，而是「AI 工具作为一次性交付工具」的本质*
   —— 大 token 换来的成果应该被固化复用，而不是每次重跑

本设计把这套思路从"动效领域的一个具体案例"提升为**跨领域的通用方法论**：
检索单位从"整个任务"细化为"**任务环节**"，复用单位从"参考"变为"**直接调用**"。

### 1.3 两条不可违反的硬规则

1. **必须先搜。** 产出型任务不允许跳过检索直接自建。
2. **不强制复用。** 搜不到合格成果就自建，这是正常结果，不是失败。

第 2 条同样重要：强制复用会引入更糟的东西（脆弱依赖、陌生代码、上游 breaking change）。
检索本身才是成本，复用是收益。

## 2. 架构

跨 agent 复用要求四层彻底解耦。任何一层混进其他层的内容，都会导致"在这个 agent 里好用、
换了个 agent 就漂"。

```
┌─ 层一 资产与契约（中立，唯一真理源）──────────────────┐
│  ~/agent-toolbox/   独立 git 仓库                        │
│    toolbox/          CLI 实现（Python 3 标准库）         │
│    index.yaml        工具索引与能力标签                   │
│    tools/            vendor 原样 + adapter                │
│    knowledge/        不可执行的成果：流程、风格、模板     │
│  唯一调用契约：toolbox run <id> --in ... --out ...        │
└─────────────────────────────────────────────────────────┘
                            ↓
┌─ 层二 skill 源文件（一份，全 agent 挂接）─────────────┐
│  ~/agent-toolbox/skills/reuse-first/SKILL.md            │
│  frontmatter: name + description（各 agent 格式一致）   │
└─────────────────────────────────────────────────────────┘
                            ↓
   ~/.claude/skills/  ~/.codex/skills/  ~/.workbuddy/skills/ …
   全部软链到同一份源文件
```

### 2.1 为什么 CLI 是唯一契约

adapter **绝不能写成 prompt 里的自然语言步骤**。
Claude Code 可能照做，Codex 可能换一种理解，同一份 skill 在不同 agent 手里行为就飘。

契约必须是**确定性的进程级接口**。所有 agent 都能用 Bash 跑一条命令，
这是唯一在所有 agent 上行为完全一致的调用方式。

```
toolbox run <id> --in <输入路径> --out <输出路径> [--opt k=v ...]
toolbox lookup <能力标签>          # 查已有工具
toolbox install <来源> --as <id>  # 装入新工具
toolbox probe                     # 探测本机各 agent 已装能力
toolbox list                      # 列出全部索引条目
```

`toolbox run` 的输出约定：成功时 stdout 输出结果路径，失败时 stderr 输出人类可读原因，
退出码非零。**不依赖任何 agent 专属的协议、hook 或 MCP 配置。**

### 2.2 为什么用独立 git 仓库

- **单一真理源**：资产永不分叉，agent 升级不影响工具箱，工具箱更新不影响 skill
- **可版本化**：能看出某个工具何时引入、为什么引入、后来为什么被标记 broken
- **可发布**：别人 clone 仓库 + 跑 install 脚本就能获得同一套能力
- **可回滚**：装坏了一个工具，回滚一次 commit 而不是逐个清理现场

### 2.3 挂接方式：复用既有 `~/.agents/` 约定

本机已有 `~/.agents/skills/` 作为跨 agent 的 skill 中枢（434 个 skill），
`~/.claude/skills/` 下全部是软链指向它。`~/.codex/skills/`、`~/.gemini/skills/` 各存各的。

因此 install 脚本的行为是：

1. 仓库内的 `skills/reuse-first/` 是源
2. 挂接 `~/.agents/skills/reuse-first` → 仓库源
3. 挂接各 agent 目录下的 `reuse-first` → 同一源

**不复制文件，只建软链。** 复制必然导致版本漂移。

`SKILL.md` 的 frontmatter 只用 `name` + `description` 两个字段 ——
这是本机所有 agent 已验证一致的最小公约数。

### 2.4 探测层的处理

"本地已装能力"这一检索源，各 agent 位置不同：
Claude Code 看 `~/.claude/skills/` 和 `~/.claude/.mcp.json`，
Codex 看 `~/.codex/`，WorkBuddy 看 `~/.workbuddy/skills/` 与连接器。

**不让 skill 正文包含这些路径。** 统一写成一条命令 `toolbox probe`，
由 CLI 扫描所有已知 agent 目录并返回结构化结果。这样 skill 层完全不含 agent 专属逻辑。

## 3. 检索：单位是环节，不是任务

### 3.1 为什么不是搜"整个任务"

搜"帮我做一个 X"几乎搜不到可用成品 —— 成品总是针对特定内容的。
但搜"提取 PDF 表格并保留合并单元格样式"、"给视频加动态字幕"、"读 Excel 做透视"，
这些**环节**有大量现成实现，别人已经把边界情况都踩过了。

真实成本几乎总是集中在环节上，不在任务整体上。

### 3.2 环节识别

把任务切成可独立验收的步骤，每步问：**这一步有没有现成实现？**

三个判定信号，命中任一即为**可检索环节**：

1. **有明确的输入/输出契约** —— 能一句话说出输入什么、产出什么
2. **有明确的失败模式** —— 容易出错的地方，大概率有人写过防护
3. **有明确的质量标准** —— 有客观判据，而不是"看起来不错"

反例对照：

| 任务片段 | 可检索 | 理由 |
|---|---|---|
| "做一个音乐搜索下载网站"（整体） | ✗ | 无稳定接口，内容高度特化 |
| "调用某站搜索接口" | ✗ | 无公开稳定 API，无契约 |
| "多站并发聚合与去重" | ✓ | 输入输出明确，有质量判据 |
| "Vue 前端列表页" | ✓ | 大量现成模板 |
| "PDF 表格提取保留合并单元格" | ✓ | 失败模式明确（合并单元格丢失） |

### 3.3 四源检索，按成本从低到高

命中即止。**前两源命中就不该再往下搜** —— 这是省 token 的主战场。

| 序 | 源 | 成本 | 查什么 | 命中后动作 |
|---|---|---|---|---|
| 1 | 本地已装 | 最低 | 已装 Skill / Connector / MCP / CLI（`toolbox probe`） | 直接调用，零安装 |
| 2 | 自己过去 | 低 | 历史会话、项目代码库、记忆文件 | 抄自己现成的实现 |
| 3 | 开源社区 | 中 | GitHub / npm / PyPI / HuggingFace | 下载装入 + adapter |
| 4 | 文章教程 | 最高 | awesome-list、踩坑记录、best practice | 转成知识条目 |

第 4 源最容易产出"看起来很有道理但没用"的噪音，只在前三源无解时启用。

### 3.4 搜索词构造

搜 `pdf table extraction tool` → 得到一堆营销文章。
搜 `github pdfplumber extract_table keep merged cells` → 直接命中实现。

**规则：关键词必须带技术名词和约束条件，不能用自然语言意图描述。**
约束条件正是把营销内容筛掉的那部分信息。

### 3.5 搜索预算（硬上限）

检索必须有上限，否则"先搜一轮"会退化成"先搜三轮"。

- 每环节最多 **4 次**检索调用
- 单任务跨环节合计 **≤ 12 次**
- 触顶即强制做决定：装冠军 / 借用 / 自建 / 放弃优化该环节

超过预算仍可继续，但必须在最终产出中显式写明"此处未穷尽检索"。

## 4. 筛选与验证

### 4.1 两段式验证

**第一段：静态筛查（不下载、不运行）**
只读 README / manifest / 包元数据，判断：

| 维度 | 看什么 |
|---|---|
| 许可证 | MIT / Apache / BSD 可用；GPL / AGPL 需谨慎；无许可证默认不可商用 |
| 活跃度 | 最近提交时间、issue 响应、是否 archived |
| 依赖 | 依赖树深度、体量、是否需要 GPU / 系统级权限 |
| 契合度 | 输入输出契约是否匹配本环节 |
| 体量 | 安装时间与磁盘占用是否值得 |

**第二段：烟测冠军**
只对静态筛查后的最优 1–2 个候选跑最小烟雾测试：能出正确结果即可。
不跑全量测试套件 —— 那是自己实现时才需要的成本。

### 4.2 三态决策

每个环节最终落到三态之一：

| 态 | 含义 | 落地 |
|---|---|---|
| **复用** | 装入 toolbox，任务中用 adapter 调用 | `tools/<id>/` + index 条目 |
| **借用** | 借鉴流程与结论，不直接调用代码 | `knowledge/<id>.md` |
| **自建** | 检索无解，自己写 | 留在项目里，不进 toolbox |

**「借用」是设计中不可省略的一态。** 灵感视频里的 Remik 方案就属于这类：
不是调用某个包，而是借鉴别人已经验证过的流程设计，用更强的模型按那个流程跑。
若只有"装"与"写"的二分，会把这整类高价值复用判成"不可用"。

### 4.3 失败即回退

烟测失败 → 标记该候选 `broken`、写入索引的失败原因、**立刻回退自建**。

绝不让"工具坏了"卡住整个任务。失败记录本身有价值 —— 下次不会重复踩同一个坑。

## 5. 落地形态

### 5.1 目录布局

```
~/agent-toolbox/
├── index.yaml                  # 全局工具索引
├── toolbox/
│   ├── __main__.py             # CLI 入口（Python 3 标准库）
│   └── ...                     # 各子命令实现
├── tools/<id>/
│   ├── vendor/                 # 别人的代码，原样，不改
│   ├── adapter.sh              # 薄适配：参数映射 + 输出约定
│   └── README.md               # 来源、许可、入口、限制
├── knowledge/<id>.md           # 不可执行的成果：流程、风格、模板
├── skills/reuse-first/
│   └── SKILL.md                # skill 源文件（唯一一份）
├── install.sh                  # 建软链 + 装 PATH
└── docs/plans/
```

### 5.2 vendor 原样，adapter 在外

**别人的代码一个字不改地放在 `vendor/`。** 所有适配逻辑写在我们自己的 adapter 里。

两个原因：
1. 满足"不重新复现" —— adapter 是薄壳，不是二次实现
2. 能安全升级上游版本 —— 改 vendor 就没法 pull 了

### 5.3 index.yaml 记录字段

单条条目携带：

```yaml
- id: pdf-table-extract
  name: PDF 表格提取（保留合并单元格）
  kind: executable            # executable | knowledge
  provides: [pdf, table-extract, xlsx-export]
  source:
    type: github              # github | npm | pypi | hf | local-skill | own-history
    url: https://github.com/...
    license: MIT
    last_commit: 2026-08-01
    stars: 1200
  entry:
    command: ./adapter.sh
    args: ["--in", "{input}", "--out", "{output}"]
  contract:
    input: PDF 文件路径
    output: CSV 或 JSON
    limits: 单文件 < 50MB，扫描件不支持
  cost:
    install_minutes: 2
    smoke_test: "./adapter.sh --selftest"
  verified: true
  status: ok                  # ok | degraded | broken
  broken_reason: null
  added_at: 2026-11-02
  added_for: "批量提取年报 PDF 表格"
```

`provides` 是**能力标签** —— 检索时按标签匹配，不按名字匹配。
名字会变、作者会改名、能力不会。

### 5.4 项目级叠加

项目可自带 `.workbuddy/toolbox/` 或约定的项目级 toolbox 目录，
其中的 `index.yaml` 与 `tools/` 与全局同构。

查找时**项目级优先**：项目里若已有同 `id` 条目，直接遮蔽全局条目，
避免在项目特定语境下误用通用版。

## 6. 反模式（写进 skill 作为禁令）

1. **复现**
   拿到源码后重新实现一遍，等于白烧 token。搬进来直接调。

2. **过度适配**
   为了适配自己的目录结构去改 vendor 里的代码。适配写在 adapter 层。

3. **索引污染**
   把只用过一次的、一次性的东西塞进 toolbox。
   toolbox 只收**可复用**的工具；一次性产出留在项目里。

4. **检索瘾**
   明明本地已有等价能力，还在开源社区里搜三小时。本地命中即止。

5. **知识当代码**
   把一份纯文档（风格指南、模板、流程）伪装成可执行工具塞进 `tools/`。
   文档进 `knowledge/`。

## 7. 触发机制

**主路径：skill description 自动触发。**
description 里写清"产出型任务开始前"这个时机，让各 agent 的 skill 匹配机制自动加载。

不往 `~/.claude/CLAUDE.md` 或 `~/.codex/AGENTS.md` 写硬规则 ——
侵入 agent 全局配置是侵入性的，且 description 已足够表达触发条件。

**兜底路径：CLI 常驻 PATH。**
`toolbox` 装到 `~/.local/bin/toolbox`。agent 在遇到"找不到现成做法"或命令失败时，
可以直接 `toolbox lookup <能力标签>` 找到替代品。这是被动触发，
不依赖 skill 匹配机制是否生效。

---

## 8. 验证方式

skill 本身没有单元测试，但有可验证的行为契约：

1. **索引可命中**：跑完后新增条目必须能被 `toolbox lookup <能力标签>` 命中
2. **烟测可跑**：每个 `executable` 条目必须带一条可执行的烟测命令，且能实际跑通
3. **契约一致**：`toolbox run` 在任意 agent 的 shell 里行为一致
4. **复用率**：一次真实任务结束后，检查该任务里是否还有"本该复用却自建"的环节 ——
   这是唯一有意义的指标

## 9. 实现范围

### 阶段一：骨架（可用）
- `toolbox` CLI：`list` / `lookup` / `run` / `probe` / `install`
- `index.yaml` schema + 两级叠加查找
- `install.sh`：建软链 + 装 PATH + 注册到 `~/.agents/skills/`
- `skills/reuse-first/SKILL.md` 完整正文
- 2 个示范工具条目（验证 schema 与调用链路）

### 阶段二：检索辅助（增强）
- 搜索词构造辅助（把自然语言意图转成带技术约束的关键词）
- 静态筛查清单自动化（拉取 repo 元数据做许可证/活跃度/体量初筛）
- 预算计数与触顶提示

### 阶段三：闭环（完善）
- 任务结束后的复用率自检
- broken 条目的周期性复检

## 10. 决策记录

| 决策点 | 选择 | 理由 |
|---|---|---|
| 适用任务范围 | 通用方法论，不限领域 | 原则本身是通用的 |
| 搬入形态 | 可执行装 toolbox，不可执行转知识 | 二分法会误杀"借用"这类高价值复用 |
| 工具箱位置 | 全局 + 项目两级叠加 | 全局跨项目复用，项目级可特化 |
| 检索源 | 四源全上，按成本排序 | 命中即止，前两源是主战场 |
| 启动门控 | 产出型任务一律先搜 | 强制"先搜"，但不强制"复用" |
| 验证方式 | 静态筛查 + 冠军烟测 | 两段式，避免全量测试成本 |
| 交互节奏 | 全自动，高置信直接装 | 减少人工往返 |
| 存储与共享 | 独立 git 仓库 + install 脚本 | 单一真理源，可发布 |
| 调用契约 | CLI 命令 | 唯一在所有 agent 上行为一致的契约 |
| CLI 语言 | Python 3 标准库 | 零依赖，跨机器最稳 |
| skill 源位置 | 仓库自包含 + 挂接 `~/.agents/skills/` | 复用本机既有跨 agent 约定 |
| 全局指令 | 不写 CLAUDE.md / AGENTS.md | 避免侵入 agent 配置 |
| 触发 | skill description + CLI 兜底 | 主路径自动，兜底被动 |
