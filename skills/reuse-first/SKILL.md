# 先复用后自建

## 何时启用

**产出型任务**开始时启用。产出型 = 会产出代码、文档、图像、视频、表格、报告、配置或流程。

**不启用**：纯问答、概念解释、改一个已有文件里的单点 bug、纯闲聊与讨论、纯思考与决策。

不确定时倾向启用。检索的边际成本远低于错误方向上的自建。

---

## 三条核心原则

### 一、搬进来的是工具本身

拿到别人的工作后**直接调用**，不要读懂后重写一遍。
重写一遍的 token 代价 ≈ 从零实现，且额外付了理解成本。

正确做法：装进工具箱 → 写薄 adapter（只做参数映射和输出约定）→ 调用。

**这不是"复现"。复现是我们要消灭的行为。**

### 二、必须先搜，但不强制复用

- 产出型任务**不允许跳过检索直接自建**
- 搜不到合格成果就自建 —— 这是正常结果，**不算失败**

强制复用会引入更糟的东西：脆弱依赖、陌生代码、上游 breaking change。
**检索本身才是成本，复用才是收益。**

### 三、检索的单位是环节，不是任务

搜"帮我做一个 X"几乎搜不到可用成品 —— 成品总是针对特定内容的。
但搜"提取 PDF 表格并保留合并单元格样式"、"把音轨对齐到视频帧"，
这些**环节**有大量现成实现，别人已经把边界情况都踩过了。

真实成本几乎总是集中在环节上，不在任务整体上。

## 执行流程

### 第 0 步：查工具箱（成本最低，先做）

```bash
toolbox lookup <能力标签>
```

能力标签用**技术名词**而非自然语言意图。
例如 `pdf table extract`、`subtitle burn`、`audio align`、`vue list page`。

命中 → 直接用，跳到第 5 步。工具箱里没有 → 继续第 1 步。

不知道有什么可查时，先看本机各 agent 已装能力：

```bash
toolbox probe
```

**若 `toolbox` 命令不存在**（command not found），按顺序尝试，任一可用即继续：

```bash
# 1. 仓库根目录下的 CLI（不依赖 PATH）
AGENT_TOOLBOX_HOME="${AGENT_TOOLBOX_HOME:-$HOME/agent-toolbox}"
PYTHONPATH="$AGENT_TOOLBOX_HOME" python3 -m toolbox lookup <能力标签>

# 2. 仓库里的启动器（若已执行过 install.sh）
"$HOME/.local/bin/toolbox" lookup <能力标签>
```

**仍不可用时不要放弃流程** —— 直接读索引继续：

```bash
cat "${AGENT_TOOLBOX_HOME:-$HOME/agent-toolbox}/index.yaml"
```

读到索引后照常做环节判定与检索，只是暂时无法用 `toolbox run` 调用已装工具
—— 那部分改为直接调用该工具的 adapter 脚本（索引条目里有 `entry.command` 路径）。

### 第 1 步：拆任务环节

把任务切成可独立验收的步骤，每步问：**这一步有没有现成实现？**

三个判定信号，命中任一即为**可检索环节**：

| 信号 | 说明 |
|---|---|
| 明确的输入/输出契约 | 能一句话说出输入什么、产出什么 |
| 明确的失败模式 | 容易出错的地方，大概率有人写过防护 |
| 明确的质量标准 | 有客观判据，而不是"看起来不错" |

三个都不命中 → 不可检索，直接自建，不浪费检索预算。

> 完整判定表与典型对照 → `references/segment-detection.md`

### 第 2 步：四源检索，按成本从低到高，命中即止

| 序 | 源 | 成本 | 命中后动作 |
|---|---|---|---|
| 1 | 本地已装（`toolbox probe`） | 最低 | 直接调用，零安装 |
| 2 | 自己过去（会话、代码库、记忆） | 低 | 抄自己现成的实现 |
| 3 | 开源社区（GitHub/npm/PyPI/HF） | 中 | 下载装入 + adapter |
| 4 | 文章教程（awesome-list、踩坑记录） | 最高 | 转成知识条目 |

**前两源命中就不再往下搜** —— 这是省 token 的主战场。

关键词必须带技术名词和约束条件，不能只用自然语言意图描述：

```
差:  pdf table extraction tool
好:  github pdfplumber extract_table keep merged cells
```

> 各源的具体查法、搜索词构造细则 → `references/searching.md`

### 第 3 步：静态筛查（不下载、不运行）

只读 README / manifest，判断五项：许可证、活跃度、依赖、契合度、体量。

许可证要点：MIT/Apache/BSD 可用；GPL/AGPL 慎用；无 LICENSE 默认不可用。

### 第 4 步：烟测冠军

只对静态筛查后的**最优 1–2 个**候选跑最小烟雾测试：能出正确结果即可。
不跑全量测试套件 —— 那是自己实现时才需要的成本。

**失败即回退**：标记 `broken`、记录原因、立刻回退自建。
绝不让"工具坏了"卡住整个任务。

### 第 5 步：接回任务

按三态决策落定：

| 态 | 含义 | 落地 |
|---|---|---|
| **复用** | 装入工具箱，用 adapter 调用 | `tools/<id>/` + index 条目 |
| **借用** | 借鉴流程与结论，不直接调用代码 | `knowledge/<id>.md` |
| **自建** | 检索无解，自己写 | 留在项目里，不进 toolbox |

**「借用」不可省略。** 有些最好的成果不是代码，而是别人已验证过的流程设计
（"动效数据流先跑通再蒸馏"这类）。只判"装"与"写"的二分，会误杀这整类高价值复用。

装入规范（vendor 原样 / adapter 在外 / index 字段）→ `references/screening-and-install.md`

## 搜索预算（硬上限）

- 每环节最多 **4 次**检索调用
- 单任务跨环节合计 **≤ 12 次**
- 触顶即强制做决定：装冠军 / 借用 / 自建 / 放弃优化该环节

超预算仍可继续，但必须在最终产出中**显式写明"此处未穷尽检索"**。

**用 CLI 计数，不要靠自觉**（超限会返回退出码 3 并强制提示）：

```bash
toolbox budget --reset --task "<任务名>"          # 任务开始时
toolbox budget --spend --segment "<环节名>"       # 每次检索前
toolbox budget                                     # 查当前用量
```

---

## 反模式（禁止）

1. **复现** — 重写一遍等于白烧 token。搬进来直接调。
2. **过度适配** — 改 vendor 代码；适配写在 adapter 层。
3. **索引污染** — 一次性东西塞进工具箱；工具箱只收可复用的。
4. **检索瘾** — 本地已有还在社区搜三小时；本地命中即止。
5. **知识当代码** — 纯文档伪装成可执行工具；文档进 `knowledge/`。

---

## 完成时自检

- [ ] 每个环节是否都做过检索？（不允许"本该复用却自建"）
- [ ] 检索预算是否触顶？触顶处是否已写明"此处未穷尽检索"？
- [ ] 新增的 `executable` 条目，烟测命令是否**实际跑通**过？
- [ ] 失败的工具是否已标记 `broken` 并记录原因？
- [ ] 新工具是否可被 `toolbox lookup <能力标签>` 命中？

**"本该复用却自建的环节还剩几个"是唯一有意义的指标。**
