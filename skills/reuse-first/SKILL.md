# 先复用后自建

## 何时启用

**产出型任务**开始时启用。产出型 = 会产出代码、文档、图像、视频、表格、报告、配置或流程。

**不启用**：纯问答、概念解释、改一个已有文件里的单点 bug、纯闲聊与讨论、纯思考与决策。

不确定时倾向启用。检索的边际成本远低于错误方向上的自建。

---

## 四条核心原则

### 一、搬进来的是工具本身

拿到别人的工作后**直接调用**，不要读懂后重写一遍。
重写一遍的 token 代价 ≈ 从零实现，且额外付了理解成本。

正确做法：装进工具箱 → 写薄 adapter（只做参数映射和输出约定）→ 调用。

**这不是"复现"。复现是我们要消灭的行为。**

### 二、必须先搜，但不强制复用

- 产出型任务**不允许跳过检索直接自建**
- 搜不到合格成果就自建 —— 这是正常结果，**不算失败**

强制复用会引入更糟的东西：脆弱依赖、陌生代码、上游 breaking change。
**检索本身才是成本，复用才是收益。**

反过来的收益也真实存在：**复用能纠正自建代码里的隐性错误**。
本次自建描边动画用 `pathLength={1}` 做"笔在写"，观感是笔速忽快忽慢 ——
它按参数匀速、不按弧长匀速，这是自己写时看不出来的错；
换成 kit 的 `evolvePath`（真实弧长）才对。另一处硬编码路径长度 `1760`，
现算实测 `2638`，"已走过"永远只涂到 2/3。
**这类坑不会出现在报错里，只会出现在成片里** —— 而别人已经替你踩过并修在代码里了。

### 三、检索的单位是环节，不是任务

搜"帮我做一个 X"几乎搜不到可用成品 —— 成品总是针对特定内容的。
但搜"提取 PDF 表格并保留合并单元格样式"、"把音轨对齐到视频帧"，
这些**环节**有大量现成实现，别人已经把边界情况都踩过了。

真实成本几乎总是集中在环节上，不在任务整体上。

### 四、质感型需求要复刻成品，不是拆零件

当需求是「好不好看」「有没有那种感觉」「质感要高级」时，
**检索目标必须从「能用的零件」切换为「最接近目标的成品」**。

原因：质感不体现在契约里。一个「玻璃卡片组件」的契约是"输入内容输出卡片"，
和"用 div 画个卡片"契约完全相同 —— 按契约筛选会把它们判为等价，
而两者的观感差一个数量级。

**功能导向的筛选只能回答"能不能"，回答不了"好不好看"。**
只按前者筛，会稳定地产出"能跑但平庸"的结果。

> 详细流程 → `references/quality-texture.md`

## 先分诊：功能型还是质感型

检索前先给任务定性。**这一步不通过，后面的检索方向就会错。**

| 类型 | 判断问句 | 检索目标 |
|---|---|---|
| **功能型** | "能不能做到？" | 能实现该契约的最小可用件 |
| **质感型** | "好不好看 / 有没有那种感觉？" | 最接近目标的**成品**，而非零件 |

两类同时存在时（最常见），**先做质感型定性** —— 它会改变整个检索策略。

**质感型的信号**（命中任一即按质感型走）：

- 用户用了「高级」「精致」「有质感」「那种感觉」「像 X 一样」这类描述
- 参考对象是一个**成品**（视频、网站、作品），而不是一份规格
- 交付物要给人看，且"看起来专业"本身是验收标准之一
- 同类东西你自己做出来"能跑但不好看"

**开源边界预检（质感型必做）**

动手前先确认：**目标质感是否真的在开源范围内？**

很多 repo 开源的是**引擎**，私有镜头库 / 品牌设计系统 / 成片素材不在其中。
作者的 README 或 CLAUDE.md 里通常写明了这点。

若质感来源不在开源范围 → **提前降级预期**，别许诺复刻。
把力气转向"用现有引擎把编排做扎实"，而不是追求不存在的观感。

> 真实教训：曾复用一个手绘视频引擎，9 个组件只用了 1 个、`spring()` 调用 0 次，
> 产出被用户评为"没有宣传视频那种质感动效"。事后查明质感来自作者私有镜头库，
> 根本不在开源仓库里。完整复盘 → `references/quality-texture.md` 第五节。

## 执行流程

### 第 0 步：查工具箱（成本最低，先做）

```bash
toolbox lookup <能力标签>
```

能力标签用**技术名词**而非自然语言意图。
例如 `pdf table extract`、`subtitle burn`、`audio align`、`vue list page`。

命中 → 直接用，跳到第 5 步。工具箱里没有 → 继续第 1 步。

**先读 `调用:` 还是 `取用:` —— 这两个词不会同时出现。** CLI 按**入口文件本身**判它能不能跑：
可执行 → 打 `调用: toolbox run <id> <参数形状>`（照抄即可）；
入口是 `SKILL.md` / 文档 → 打 `取用: 读 …（不能 toolbox run）` + `用法:` 一行说明，
这时候**别把那句说明当命令敲**。参数形状只来自条目声明，CLI 不替你猜。
`--in/--out` 只是部分工具的契约，不是全局约定 —— 照记忆拼参数会浪费一轮调用。
`许可:` 也是现场必读的：非商用 / 需署名 / 需授权的约束打在这里，不在你脑子里。

**`status` 四态，决定了下一步做什么**：

| status | 含义 | 动作 |
|---|---|---|
| `ok` | 现在能跑 | 可执行的直接 `toolbox run`；文档型条目按其方法调用 |
| `needs_setup` | 代码在位，前置未就绪（venv、模型、外部服务） | 先跑 `前置:` 那行的 setup 命令，再烟测 |
| `unavailable` | 来源不可达 / 装不上，暂时性 | 读原因，判是否值得等；否则换候选 |
| `broken` | 实测跑不通 | `toolbox run` 会拒绝；按第 4 步回退 |

`verified: true` 的含义**跟着条目形态走**，CLI 在 `验证:` 那行会说清是哪种：
可执行条目 = **登记当时烟测真跑通**；文档 / 知识条目 = **该流程或结论在真实任务里走过一遍**
（它没有可执行体，不可能"烟测"）。两种都只代表当时的观察，不代表你这台机器现在能跑。
把它当历史事实，不当当前保证。

不知道有什么可查时，先看本机各 agent 已装能力：

```bash
toolbox probe
```

**若 `toolbox` 命令不存在**（command not found），按顺序尝试，任一可用即继续：

```bash
# 1. 仓库根目录下的 CLI（不依赖 PATH）
AGENT_TOOLBOX_HOME="${AGENT_TOOLBOX_HOME:-$HOME/agent-toolbox}"
PYTHONPATH="$AGENT_TOOLBOX_HOME" python3 -m toolbox lookup <能力标签>

# 2. 仓库里的启动器（若已执行过 install.sh）
"$HOME/.local/bin/toolbox" lookup <能力标签>
```

**仍不可用时不要放弃流程** —— 直接读索引继续：

```bash
cat "${AGENT_TOOLBOX_HOME:-$HOME/agent-toolbox}/index.yaml"
```

读到索引后照常做环节判定与检索，只是暂时无法用 `toolbox run` 调用已装工具
—— 那部分改为直接调用该工具的 adapter 脚本（索引条目里有 `entry.command` 路径）。

### 第 1 步：拆任务环节

把任务切成可独立验收的步骤，每步问：**这一步有没有现成实现？**

三个判定信号，命中任一即为**可检索环节**：

| 信号 | 说明 |
|---|---|
| 明确的输入/输出契约 | 能一句话说出输入什么、产出什么 |
| 明确的失败模式 | 容易出错的地方，大概率有人写过防护 |
| 明确的质量标准 | 有客观判据，而不是"看起来不错" |

三个都不命中 → 不可检索，直接自建，不浪费检索预算。

> 完整判定表与典型对照 → `references/segment-detection.md`

### 第 2 步：四源检索，按成本从低到高，命中即止

| 序 | 源 | 成本 | 命中后动作 |
|---|---|---|---|
| 1 | 本地已装（`toolbox probe`） | 最低 | 直接调用，零安装 |
| 2 | 自己过去（会话、代码库、记忆） | 低 | 抄自己现成的实现 |
| 3 | 开源社区（GitHub/npm/PyPI/HF） | 中 | 下载装入 + adapter |
| 4 | 文章教程（awesome-list、踩坑记录） | 最高 | 转成知识条目 |

**前两源命中就不再往下搜** —— 这是省 token 的主战场。

关键词必须带技术名词和约束条件，不能只用自然语言意图描述：

```
差:  pdf table extraction tool
好:  github pdfplumber extract_table keep merged cells
```

> 各源的具体查法、搜索词构造细则 → `references/searching.md`

### 第 3 步：静态筛查（不下载、不运行）

只读 README / manifest，判断五项：许可证、活跃度、依赖、契合度、体量。

许可证要点：MIT/Apache/BSD 可用；GPL/AGPL 慎用；无 LICENSE 默认不可用。

**质感型任务额外一维：纳入「质感件」。**

下列组件的增量不在契约里，因此**不参与「契合度」淘汰**，只要存在就必须纳入候选：

| 质感件类型 | 识别信号 |
|---|---|
| 纵深 / 层次 | 景深、遮挡、前景模糊、分层背景、玻璃拟态 |
| 物理缓动 | `spring`、弹簧参数、惯性、过冲 |
| 纹理 / 材质 | noise、grain、纸纹、渐变网格、杂色 |
| 光效 | 发光、泛光、体积光、阴影投射 |
| 编排 / 运镜 | 相机系统、pose 序列、连续缩放、转场编排 |

一句话：**看到"让东西变好看"的组件，即使当下想不到用在哪，也先收进候选。**

**筛完剩的候选，还要过一道可得性预检**（三条，任一不通就别投验证预算）：
可达（**用真正会去下载的那个客户端探**，不是用 curl 探）、
可装（目标环境有没有 wheel / release 里有没有 asset）、
不静默出错（跑最刁的样本，检查**丢了什么**，而不是只看有没有产物）。

**可达是「源 × 下载器 × 时段」的矩阵，不是域名属性。** 实测：2026-11-03 晚 `curl` 同一 URL
返回 200，而 pip / uv（rustls）对 `pypi.org/simple` 一律 `ConnectionReset`（TLS 指纹被 reset）；
`github.com` 的 git 端点超时，`codeload` / `api.github.com` 却通。
**11-04 复测同一条 `pip download` 退出码 0、wheel 落盘** —— 格子会翻，所以每次现测，
别把上一次的绕行当永久规则。
所以探法 = 把工具声明的安装命令原样跑一次。三条绕行按"改调用侧、不动全局配置、
不进工具箱"处置：codeload tarball 代替 clone；`git -c http.proxy=` 局部覆盖；
`curl` 拉 wheel + `pip --no-index` 离线装。

真实教训：`huggingface.co` 本机返回 `000`；某引擎没有 Python 3.14 的 wheel；
某 TTS 退出码 0、时长合理，却把中英混排里的 `AI` 静默丢掉了。


### 第 4 步：验证冠军 —— 只认 L3 以上

烟测有深浅，而**浅层烟测会放过一个完全错误的实现**。四级阶梯：

| 级 | 断言的是 | 能骗过它的东西 |
|---|---|---|
| L1 接线 | import 成功、代码里有调用 | 注释写着"弹簧推开"、代码里是常量 |
| L2 调用被接受 | 参数被认、退出码 0、有产物 | TTS 正常出 WAV，但把拉丁词 `AI` 悄悄丢了 |
| L3 产物里有效果 | 从**产物本身**读出预期物理量 | 时长对得上，字幕却比人声早 80ms；验收脚本自己推公式 |
| L4 本任务的刁样本 | 用最可能出错的输入做 L3 | 通用样例过了，中英混排 / 边界帧挂了 |

**下限**：影响交付物的环节做到 **L3**；质感型与"时序 / 对齐"类环节做到 **L4**。
L1、L2 不足以支撑索引里的 `verified: true`。

**标杆跑不动时，基线可以降级，验证不许降级。** 别人发的"参考成品"常常只是产物
（帧 / 图 / 文档）而不是可跑工程 —— 某解说片工具的 `examples/rag/` 只有 23 张成品帧 +
9 个镜头源码目录，**没有 `package.json`**，重跑等于重拍一片。三档处置缺一不可：
① 基线改成**结构同构比对**（用工具自己的出帧命令，与样片逐项对"画面要素清单"）；
② 说清**真正的质量闸门在工具的哪一步**（它的确认点 / 样片闸门），别用同构比对冒充观感验收；
③ 本轮**验不到的元素逐条列出并写明顺延到哪一步**，`verified: false` 配顺延位置，不写"大致没问题"。
   逐条列的意思是**把占位数据的派生项 grep 干净**（`export const X = []`、`len ? … : []`、
   `.map` / `.slice` 作用在空数组上）—— 实测那一轮列出的是七项（章节卡 / 进度条标签 /
   分隔线 / HUD / 流程轨 / 字幕带 / 末段边界），不是脑子里那两三项。
   **①的清单与③的清单必须互斥**：一边宣称"比对了五要素"、一边承认其中两要素在空工程里
   根本画不出来，就是自欺。

L3 的取法决定它有没有用 —— **从最终产物回读，不从中间日志读**：

- 视频 → 从成片抽帧（`ffmpeg` 抽取，不是重新渲染），逐帧扫描黑屏 / 溢出 / 亮度
- 音画对齐 → 从渲染好的 MP4 里回读 PCM 量 onset（本次就是靠这一步才暴露字幕前移）
- 编排层改动 → **静帧验收**：截一张代表性帧看像素，而不是读代码
- 文本 / 语音 → 断言"**丢了什么**"而不是"产了什么"：回读比对字形，
  只 `[[ -s out.wav ]]` 的烟测抓不到静默降级

**验收脚本必须读产物，不许自己重推公式。** 实测事故：自建校验里有个闸
"按理想公式推算镜头界"，它 PASS，而分镜表里真正写出来的那一列是坏的 ——
相邻镜头 16–52 帧空场、16/19 镜停留不足。**重推公式的校验只证明"你和你的错误理解一致"**，
等于没查。同一条也适用于校验脚本本身：只看 stdout 文本、不判退出码与 stderr 的断言会给假 PASS
（工具抛 Traceback 时前半段输出照样匹配关键词，我自己写的测试就中招过一次）。

**借用别人自带的 QC 闸门时，先验它能不能解析你的文本。** 工具的校验器读的是**格式**，
格式是隐式契约，而解析失败通常是静默的：
正则要求 `SC\d\d\s+`（id 后必须有空格），把 19 条压成一行只解析出 5 条；
`re.search` 取首个同名短语，白名单读出 **0 条 → 任何超标都判不出来**；
更绕的是"无 glitch"的镜头被当成白名单键，等于**要求它们非闪不可**。
落地判据：**让校验器打印它解析到的条数，与你预期的条数核对；0 条 ≠ 全部合格。**

**观感对比前先归一化干扰量**：响度不一致时，"响一点的那个天然占便宜"，
测出来的不是质感而是增益。先统一响度（LUFS）、尺寸、DPI、时长、取样位置，
再让人或模型挑。
**不归一化得到的偏好不能写进索引** —— 它测的是增益，不是质感。

**失败即回退**：标记 `broken`（暂时性障碍标 `unavailable`）、记录原因、立刻回退自建。
绝不让"工具坏了"卡住整个任务。

### 第 5 步：接回任务

按**四态决策**落定：

| 态 | 何时用 | 落地 |
|---|---|---|
| **复用** | 契约明确契合，可直接调用 | `tools/<id>/` + index 条目 |
| **借用** | 只有流程/结论有价值，无代码可调 | `knowledge/<id>.md` |
| **标杆复刻** | 需求是质感 / 风格 / "要有那种感觉" | 先跑通成品，再只换内容层 |
| **自建** | 检索无解，自己写 | 留在项目里，不进 toolbox |

**「借用」不可省略。** 有些最好的成果不是代码，而是别人已验证过的流程设计
（"动效数据流先跑通再蒸馏"这类）。只判"装"与"写"的二分，会误杀这整类高价值复用。

**「标杆复刻」不可省略。** 它和「复用」的区别：复用是拿零件回来自己装配，
复刻是**先让别人的成品跑起来，再换掉里面的内容**。质感型任务只有后者能保住观感。

复刻的四步纪律见 `references/quality-texture.md`，核心是：
**第 2 步跑通之前不许读它的实现代码。** 先看效果，后看代码 ——
读了代码会让人"觉得懂了"，从而跳过去自己重写，那就是复现。

**复用 = 连它的流程契约一起接，不是只拿代码。** 一整套 agent skill 自带用户闸门、
确认点、preflight —— 跳掉它们就等于把工具降级成一堆零件，质感与一致性正是从那里面来的。
写一份 `TOOL_INTERFACE.md`：命令原文 + 参数 + 产物路径 + 它要求的停顿点。

**工具的反向硬约束会重塑你的内容层，用事实满足它，不要用修辞糊过去。**
实测三条：章名 7 字压成 4 字（进度条槽宽 = 1280 ÷ 章数，硬规 ≤6 字）；
某章只有 55s 卡在"每章 ≥60s"下，补的不是形容词而是一条有出处的工程事实
（启用工具时系统提示税 = 346 token，AWS Bedrock 文档表格）—— 既过闸又把论点推进画面；
内容直接写进工具**唯一的输入位**（`script/narration.txt`），不在自己目录里留副本，
否则两份文案必然漂移，验收脚本还得指回去。

**借来的坑清单只有变成机器闸才算借到。** "片尾压黑吃掉末镜头收尾"在别人 `lessons.md` 里
是**第三次**记录，本轮仍差点踩中（最后一个动作几乎在暗场里做完），拦住它的是派单前手算帧界。
落地：别人教训里的每一条可数化的坑，转成本任务的一条断言或一次帧界对账。

**委派出去的工作产物要自己验，但别据一次"还没出现"就判定它没做。**
实测两向都错过：subagent 回报"已写文件"时文件确实没落盘、还给过两个 404 的 URL；
稍后它自己完成了 130 行的调研稿。**总结是意图，不是产物** —— 落盘、条数、来源逐一自己核，
但核的时机是完成通知之后。

装入规范（vendor 原样 / adapter 在外 / index 字段）→ `references/screening-and-install.md`

## 预算：检索与验证分两本账（硬上限）

| 账 | 上限 | 计什么 |
|---|---|---|
| **检索** | 每环节 ≤ **4** 次，单任务 ≤ **12** 次 | 找候选：搜仓库、读 README、比文档 |
| **验证** | 每环节 ≤ **3** 次，单任务 ≤ **8** 次 | 跑候选：装依赖、跑烟测、做 L3/L4 |

**为什么必须分账**：把"实测淘汰 5 个配音引擎"记进检索账，会读出 13/12 的违规，
而那其实是**必要且成功的验证**。混账的代价不是超支，是记录者开始少报 ——
预算机制一旦被证明会冤枉诚实的人，它就废了。

```bash
toolbox budget --reset --task "<任务名>"                        # 任务开始时
toolbox budget --spend --segment "<环节名>"                     # 每次检索前
toolbox budget --spend --segment "<环节名>" --kind verify       # 每次验证前
toolbox budget                                                   # 查两本账
```

触顶即强制做决定：装冠军 / 借用 / 标杆复刻 / 自建 / 放弃优化该环节。
**超限会返回退出码 3 并打印提示 —— 靠机制，不靠自觉。**
超预算仍可继续，但必须在最终产出中**显式写明"此处未穷尽检索"**
（验证超限则写"此处未验证到 L3"）。

## 反模式（禁止）

1. **复现** — 重写一遍等于白烧 token。搬进来直接调。
   **变体：读代码抽原语** —— 把参考仓库的 demo 读完，抽出几个"原语"塞进自己工程，
   文件名换成自己的。这是复现，只是换了名字。正确做法是先让 demo 跑通。
2. **过度适配** — 改 vendor 代码；适配写在 adapter 层。
3. **索引污染** — 一次性东西塞进工具箱；工具箱只收可复用的。
4. **检索瘾** — 本地已有还在社区搜三小时；本地命中即止。
5. **知识当代码** — 纯文档伪装成可执行工具；文档进 `knowledge/`。
6. **按契约筛质感** — 拿"输入输出是否匹配"去淘汰质感件。
   档次差异、层次、物理缓动都不在契约里，这样筛必然把好东西筛掉。
7. **拿零件当成品** — 质感型任务里，收了 5 个组件就以为复刻完成。
   组件的正确用法是"在原成品里看它怎么被用"，不是单独拎出来用。
8. **跳过开源边界预检** — 追一个根本不在开源范围里的观感。
   很多 repo 开源引擎、不开源作品，动手前必须确认上限在哪。
9. **把接线当验证** — grep 到 import、退出码 0、产物非空，就登记 `verified: true`。
    这只到 L2；实际成片可能整体错位半帧、字幕跑在人声前面。
    **验证结论必须来自产物回读，不来自日志。**
10. **用注释冒充实现** — 文档写"已沉淀进工具箱 / 已用弹簧推开"，
    工具箱里 grep 不到那条坑，代码里那个变量是常量。
    **任何"已沉淀 / 已接上"的声明都要能被 grep 或像素复核；对不上就是没做。**
11. **拿别人的偏好当自己的结论** — 未归一化响度 / 尺寸 / 时长就 A/B，
    然后把"响的那个更好"写进索引。
12. **编造调用契约** — 不读条目声明的 `entry.usage`，凭记忆或照别的工具的样式拼参数。
    **变体：把散文拼成命令** — 入口是 `SKILL.md` 的条目也被打成 `toolbox run <id> <一句说明>`，
    看着能抄，敲进去必挂。能不能 run 认**入口文件本身**，不认 `kind` 的名字。
13. **自推公式的校验器** — 验收脚本按规范推算"应该是多少"，而不是读真正产物。
    它 PASS 而产物是坏的。**重推公式只证明你和你的错误理解一致。**
14. **把坑清单当防护** — 借来的 `lessons.md` 读一遍就开工；没转成可跑断言的坑会重复踩
    （同一条坑第三次命中）。
15. **回写别人的仓库** — 把新坑写进 vendor 的 `lessons.md`；重取上游即被冲掉，
    而工具箱"看起来有这条经验"其实没有。写自己的 `knowledge/`，贡献走 issue / PR。
16. **拿一个客户端的可达性替所有客户端表态** — `curl` 通就判"源可达"，
    然后 pip / uv / git 各自撞在 TLS 指纹与代理上。可达是**源 × 下载器 × 时段**的矩阵：
    反方向同样成立 —— 某晚 pip 全挂，次日同一条命令就退出码 0，别把任一格的结论当永久事实。
17. **把"已经修正过"当成"已经核实过"** — 证伪后改写完新描述就不再核它。
    实例：烟测从"渲染参考片"改成"与样片对五要素"，其中字幕带 / 进度条在空工程里
    是占位数组的派生量，**根本画不出来** —— 修正后的句子照样发假证书。
    **每改写完一次，把新句里每个"已对过"的项再问一遍：它在没有真实数据的工程里出得出像素吗。**

## 完成时自检

- [ ] 每个环节是否都做过检索？（不允许"本该复用却自建"）
- [ ] 是否做过**功能型 / 质感型分诊**？质感型是否走了标杆复刻？
- [ ] 质感型任务：参考仓库的 demo 是否**先跑通过**再改内容？
- [ ] 质感型任务：**质感件使用率**是多少？
      （收了 N 个组件只用了 1 个 = 警号，说明还是按契约在筛）
- [ ] 位移类动画是否**按运动语义分派缓动**？有落点的用 spring；
      穿越画面的行程保持线性（给行程套弹簧 = 对象在终点自己刹车）
- [ ] 每条"已验证"是否到 **L3 以上**（从产物回读）？有没有 L1 / L2 冒充？
- [ ] 每条验收断言读的是**真正产物**，还是脚本自己重推的公式？
      校验命令是否同时判**退出码与 stderr**（只 grep stdout 会给出假 PASS）？
- [ ] 借用别人自带的 QC 闸门时，是否核对过**它解析到的条数 == 我写的条数**？
      读出 0 条是否当成"全部合格"了？
- [ ] 标杆跑不动时：同构比对的要素清单写了吗？验不到的元素是否逐条写了**顺延到哪一步**？
      两份清单是否**互斥** —— 有没有把"空工程里根本画不出来"的项算进已比对？
- [ ] **被证伪后改写过的句子**（烟测描述、要素清单、`verified` 说明）有没有再核一遍它**自己**？
      修正后的描述同样可能含不可验项 —— 别把"改过"当"核过"。
- [ ] 工具的硬约束（章名长度 / 每章最短时长 / 槽宽）是否用**有出处的事实**满足，
      而不是改工具或堆修辞？内容是否只存在一份、写在工具的输入位上？
- [ ] 借来的坑清单是否转成了本任务的可跑断言？新坑写在自己的 `knowledge/`
      而不是 vendor 的文件里？
- [ ] 可得性是否用**工具声明的那条安装命令**验过（不是 curl 单独表态）？
      依赖装在调用侧、vendor 里没长 `node_modules`？钉版本清单里有没有已知坏版本？
- [ ] 编排层改动是否做过**静帧验收**？注释描述与像素是否一致？
- [ ] 机械扫描（grep 类指标）是否**排除了注释**？
- [ ] 观感 A/B 之前是否归一化了响度 / 尺寸 / 时长 / 取样位置？
- [ ] 检索与验证**两本账**分别是否触顶？触顶处是否写明"未穷尽 / 未验证到 L3"？
- [ ] 新增 `executable` 条目：`entry.usage` 是否就是 adapter 真正接受的参数形状？
      前置未就绪是否标 `needs_setup` 而非 `ok`？`verified: true` 是否配了 `verified_at`？
- [ ] 失败的工具是否标记 `broken`（暂时性障碍标 `unavailable`）并记录原因？
- [ ] 新工具 / 新坑是否可被 `toolbox lookup <能力标签>` 命中？
      **声称"已沉淀"的内容，逐条 grep 得到关键词才算沉淀**
- [ ] 若这轮改动要把工具箱发布出去：设计文档、试错日志、对其它本地项目的引用是否都留在本机？
      （判据：**clone 的人会不会用到它** —— 过程记录对作者有意义，对使用者是噪音）

**四个核心指标：**
- "本该复用却自建的环节还剩几个"
- "质感件使用率"——质感型任务里，收了却没用上的质感件数量
- "L3 以上验证覆盖率"——影响交付物的环节里，有几条结论来自产物回读
- "机器闸覆盖率"——借来的坑清单里，有几条变成了本任务能跑的断言
  （只在文档里复述过的坑不计入，那等于 0）
