# 检索细则

## 先分型：功能型还是质感型

**同一个检索动作，两类任务的搜索词和目标完全不同。**

| | 功能型 | 质感型 |
|---|---|---|
| 问句 | 能不能做到 | 好不好看 / 有没有那种感觉 |
| 检索目标 | 组件、库、脚本 | **成品**：demo 视频、示例站、模板默认渲染 |
| 搜什么词 | 技术名词 + 约束 | 「demo」「example」「showcase」「starter」「template」 |
| 命中判据 | 输入输出契约匹配 | **观感接近目标** |
| 下一步 | 装进 toolbox | **先跑起来，再换内容** |

质感型任务的完整流程 → `quality-texture.md`

**典型误判**：拿功能型的搜法去搜质感型需求，会搜到一堆"能实现该功能"的库，
全部装上之后观感依然平庸 —— 因为搜的是能力，不是作品。

---

## 四源顺序（成本从低到高，命中即止）

| 序 | 源 | 成本 | 查什么 | 命中后动作 |
|---|---|---|---|---|
| 1 | 本地已装 | 最低 | `toolbox probe` 输出的各 agent skill 与 MCP | 直接调用，零安装 |
| 2 | 自己过去 | 低 | 历史会话、项目代码库、记忆文件 | 抄自己现成的实现 |
| 3 | 开源社区 | 中 | GitHub / npm / PyPI / HuggingFace | 下载装入 + adapter |
| 4 | 文章教程 | 最高 | awesome-list、踩坑记录、best practice | 转成知识条目 |

**前两源命中就不再往下搜** —— 这是省 token 的主战场。

第 4 源最容易产出"看起来很有道理但没用"的噪音（营销文章、过时的最佳实践、
AI 生成的垃圾总结），只在前三源无解时启用。

## 源 1 的具体查法

`toolbox probe` 会扫出本机各 agent 已装的 skill 与 MCP。命中后：

- 工具箱 `toolbox lookup` 命中 → **照它打印的 `调用:` 行拼参数**，那是索引里
  `entry.usage` 的原样转告；`status: needs_setup` 就先跑打印出来的 `前置:`
- skill 命中 → 直接按该 skill 的说明调用
- MCP 命中 → 直接用对应工具
- 都不命中 → 进入源 3

不要因为「probe 结果里看着不相关」就跳过 —— 能力标签不一定出现在名字里。

## 源 2 的具体查法

自己过去的东西成本最低但最容易被忽略。三处：

- 历史会话 —— 用会话检索工具搜能力关键词
- 项目代码库 —— `grep` 关键函数名/依赖名，看是否已实现过
- 记忆文件 —— 查工作区记忆里是否已沉淀过同类工具

命中后可以直接把已有实现当工具用，或抄进 adapter。

## 源 3 的搜索词构造

**关键词必须带技术名词和约束条件，不能只用自然语言意图描述。**
约束条件正是把营销内容筛掉的那部分信息。

```
差:  pdf table extraction tool
差:  怎么从 pdf 里提取表格
好:  github pdfplumber extract_table keep merged cells
好:  pypi pdfplumber table extraction merged cell
好:  npm pdf-table-extract preserve-rowspan
```

构造原则：
1. 带**技术名词**（库名、格式名、协议名），不是「工具」「方案」这类泛词
2. 带**约束条件**（保留合并单元格、离线、大文件）
3. 加**平台限定**（github / pypi / npm）直接指向可获得源码的地方

## 源 4 的处理

文章类结果几乎不能直接调用，只能**转成知识条目**（`knowledge/<id>.md`）。

转的时候要写清楚：
- 这套流程的**结论**是什么（不是原文摘抄）
- **什么情况下适用、什么情况下不适用**
- 有没有**边界条件**（成本、副作用）

一篇 awesome-list 本身不构成知识条目 —— 它是索引，不是内容。
要读到具体那篇文章的实际做法，提取出可执行的步骤，才算知识条目。

## 预算：检索与验证分两本账

| 账 | 每环节 | 单任务 | 计什么 |
|---|---|---|---|
| **检索** | 4 | 12 | 找候选：搜仓库、读 README、比文档 |
| **验证** | 3 | 8 | 跑候选：装依赖、跑烟测、做 L3 / L4 |

为什么分账：**"实测淘汰 5 个配音引擎"是验证成本，不是检索失控。**
混记会让诚实的记录读出违规（13/12），于是人开始少报 —— 预算机制就失效了。
超出检索上限的部分要标"（触顶后实测）"，超出验证上限的部分要标"未验证到 L3"。

```bash
toolbox budget --spend --segment "配音引擎"                    # 检索
toolbox budget --spend --segment "配音引擎" --kind verify       # 验证
```

触顶后的决定只有五种：装冠军 / 借用 / 标杆复刻 / 自建 / 放弃优化该环节。

## 质感型的搜索词

质感型任务的关键词不指向功能，而指向**成品**：

```
差:  remotion glassmorphism component
好:  remotion template demo showcase 1080p render example
好:  "<库名>" starter kit example gallery motion graphics
好:  site:github.com "<库名>" "npm run render" OR "stories"
```

判据：**搜索结果里有没有可以直接跑起来的成片**。只有 API 文档说明它还在零件层。

预算的意义不是限制质量，而是防止「先搜一轮」退化成「先搜三轮」。
检索本身是成本，复用才是收益。
